## B. Executive Summary

- **Overall Health Assessment:** ONUSLY has a solid core authorization model in several backend service layers (atomic DynamoDB transactions on proof submission/approval, owner vs. approver isolation in goal/proof/approval services, strict CSP/XSS guards on `/uploads/` headers), and its public landing page renders quickly on desktop (`LCP 1.82s`, `CLS 0.0016`) with HTTP->HTTPS redirect and Let's Encrypt TLS valid through `2027-02-23`. However, **live production runtime testing and deep cross-layer inspection uncovered critical production-breaking defects across Nginx routing, real-time WebSockets, upload authorization, Windows native-pipe installation, and EC2 operations.**
- **Finding Counts (20 Total):**
  - **CRITICAL:** 3 (`API-001`, `PROOF-001`, `SECURITY-001`)
  - **HIGH:** 8 (`WEB-001`, `WEB-002`, `AWS-001`, `AWS-002`, `AWS-003`, `SECURITY-002`, `WIN-001`, `WIN-002`)
  - **MEDIUM:** 6 (`AWS-004`, `SECURITY-003`, `WEB-003`, `GOAL-001`, `API-002`, `WIN-003`)
  - **LOW:** 1 (`PERF-001`)
  - **INFORMATIONAL:** 2 (`INFO-001`, `INFO-002`)
- **Major Broken Production Journeys Observed:**
  1. **Real-Time WebSocket Delivery Completely Broken in Production (`API-001`):** Every authenticated browser session in EC2 `journalctl` disconnects after 5–6 seconds with `websocket: close 4403: Authentication timed out` because `ServeWSWithValidator` authenticates via the `token` HttpOnly cookie and skips sending `{"type":"auth.success"}`.
  2. **All PNG/JPG/JPEG/GIF Proof Photos Return 404 in Production (`PROOF-001`):** Nginx's nested static cache regex inside `location /` (`location ~* \.(?:css|js|woff2?|svg|png|jpg|jpeg|gif|ico)$`) intercepts `/uploads/proofs/*.png|jpg|jpeg|gif` before the Go backend proxy rule, returning `404 Not Found`.
  3. **SPA Deep Links / Page Refresh Broken (`WEB-001`):** Refreshing `/goals`, `/goals/:id`, `/approvals`, `/friends`, `/communities`, `/wellbeing`, or `/auth` hits the Go API regex in Nginx instead of `index.html`, returning raw `missing authorization header` (`401`) or `404 page not found`.
  4. **Landing Page Mobile Layout Broken (`WEB-002`):** Unwrapped header navigation (`film.css`) forces `390px` and `320px` viewports to widen to `523px`, creating a black margin bar on the right and overlapping brand/nav items.
- **Major Windows Issues (`WIN-001`, `WIN-002`, `WIN-003`):** `OnuslySetup.exe` dials the named pipe without `SECURITY_IDENTIFICATION` SQOS flags (`0` instead of `SECURITY_SQOS_PRESENT | SECURITY_IDENTIFICATION`), causing the agent's strict `impLevel != 1` check to reject every installer `ping`/`pair-request`/`pair-poll` call (`got 2`), AND `OnuslySetup.exe` installs as an unprivileged `HKCU` VBS runner rather than the hardened `LocalService` Windows service model assumed by `install.ps1` and `ONUSLY_Shield_Toggle.exe`.
- **Major AWS Issues (`AWS-001`–`AWS-004`):** Root 8 GB EBS volume (`vol-087b33f32d9b0d6ca`, unencrypted) is at **91% capacity (`810 MB` free)**; SQS queues `proof-events` and `approval-events` do not exist (`NonExistentQueue`), forcing volatile in-memory queuing; proof uploads live solely on local EC2 EBS; zero CloudWatch alarms and disabled detailed monitoring.
- **Major Security Concerns (`SECURITY-001`–`SECURITY-003`):** `GET /uploads/proofs/*` only verifies that the caller is *any* authenticated user (no owner/approver authorization check); `RequireUserToken`/`RequireDeviceToken` middleware are defined but never attached to routes; `Revoke All Sessions` skips `device` tokens and fails open on DB error.
- **Blocked Tests:** Authenticated end-to-end UI workflows (Account A <-> Account B goal/proof/approval/chat execution) due to absence of pre-provisioned QA OAuth tokens, and live Windows runtime execution due to absence of a Windows VM.

### [API-001] — WebSocket Cookie Authentication Omits `auth.success`, Causing Immediate 6s Disconnect (`4403`) for All Web Users

Severity: CRITICAL  
Confidence: CONFIRMED  
Status: FIXED AND VERIFIED (live EC2 binary deployment pending)  
Component: Realtime WebSocket Gateway (`internal/realtime/handler.go`) & WebSocket Client (`frontend/src/lib/websocket.js`)  
Environment: Production (`wss://onusly.duckdns.org/ws`) and local dev  
Affected versions or commits: `db9cb11` (`main`)

**1. What is the issue?**  
When an authenticated web user opens a WebSocket connection, the browser sends the `token` HttpOnly cookie (set at login). The Go WebSocket handler sees `preAuthUser != nil`, registers the client, and exits `ServeWSWithValidator` **without emitting `{"type": "auth.success"}`**. Meanwhile, the frontend `WebSocketManager` waits `6000ms` for `{"type": "auth.success"}` before closing the socket with code `4403` ("Authentication timed out") and permanently halting reconnection (`isManuallyClosed = true`).

**2. Expected behavior**  
Once the server authenticates the WebSocket connection (either via pre-upgrade cookie/Bearer header OR first-message `{type:"auth"}` frame), it sends `{"type":"auth.success","payload":{"userId":...,"handle":...}}` (or handles an explicit client `{type:"auth"}` probe cleanly), allowing `WebSocketManager` to transition to `ConnectionState.AUTHENTICATED` and keep the socket open for real-time unlocks, chat, and notifications.

**3. Actual behavior**  
Every browser session connects to `/ws`, gets logged as `[WebSocket] Connected: ...` on the server, never receives `auth.success`, hits client `AUTH_TIMEOUT_MS` (`6000ms`), and closes cleanly with WebSocket close frame `4403: Authentication timed out`. No real-time unlocks, chat messages, or limit alerts arrive over WebSocket.

**4. Why is it happening?**  
Confirmed root cause:  
- `internal/auth/handler.go:93` (`GoogleLogin`) and `154` (`GoogleCallback`) set cookie `token=<jwt>; HttpOnly; Secure; SameSite=Lax; Path=/`.  
- Because the frontend and backend share origin `https://onusly.duckdns.org`, the browser attaches `Cookie: token=...` to the `wss://onusly.duckdns.org/ws` upgrade request.  
- `internal/realtime/handler.go:247-284` populates `preAuthUser` from the cookie, upgrades the socket, calls `hub.Register(client)`, starts `WritePump`/`ReadPump`, and returns immediately **without sending `auth.success`** (whereas only `handleHandshake` at line 368 sends `auth.success`).  
- `frontend/src/lib/websocket.js:121-206` sends `{type:"auth", token}` in `ws.onopen`, stays in `AUTHENTICATING`, ignores all non-`auth.success` messages, and after `6000ms` (line 111) calls `_handleAuthFailure(ws, generation, "Authentication timed out")`, sending close code `4403` and setting `this.isManuallyClosed = true` (line 263).  
- `Client.ReadPump()` on the server reads `{type:"auth"}` as a regular message, silently drops it in `HandleClientMessage`, and logs the `4403` close 5–6 seconds later.

**5. Evidence**  
Live production `journalctl -u onusly` on `i-0dfb8ec15543e8457` (2026-11-26 UTC; PII redacted):

Source references: `internal/realtime/handler.go:247-284,368-375`, `internal/realtime/hub.go:183-213`, `frontend/src/lib/websocket.js:11,111-176,259-275`, `internal/auth/handler.go:93`.

**6. Steps to reproduce**  
1. Sign into `https://onusly.duckdns.org` with Google (`POST /auth/google` sets the `token` cookie).  
2. Open Dashboard (`/dashboard`) or Goal Detail (`/goals/:id`) and open Browser DevTools -> Console / Network (WS).  
3. Observe `wss://onusly.duckdns.org/ws` connect, receive no `auth.success`, emit `[WebSocket] Authentication timed out on client` after 6 seconds, and close with code `4403`.

**7. User and system impact**  
100% of real-time web updates fail in production: instant unlock banners upon partner approval, real-time goal rejection updates, live chat message push, live friend request updates, and `wellbeing.limit_reached` notifications never arrive without manual page refreshes.

**8. Recommended resolution**  
In `internal/realtime/handler.go:278-284`, when `preAuthUser != nil`, emit the exact same `{"type":"auth.success","payload":{"userId":preAuthUser.ID,"handle":preAuthUser.Handle}}` message immediately after `hub.Register(client)` (via `client.SendEvent(...)` or `conn.WriteMessage` before `ReadPump`), AND ignore/acknowledge an idempotent follow-up `{"type":"auth"}` message in `HandleClientMessage` if already authenticated. Ensure `ReadPump` updates `auth` cleanly and tests cover cookie-authenticated WS handshakes against `WebSocketManager`.

**9. Verification criteria**  
1. Unit/integration test authenticating `/ws` with an `HttpOnly` `token` cookie verifies `auth.success` arrives immediately and socket stays open past 10 seconds.  
2. Production DevTools WS frame log shows `auth.success` received within <1s and dashboard live-sync stays green.

### [PROOF-001] — PNG, JPG, JPEG, and GIF Proof Uploads Return HTTP 404 in Production Due to Nginx Regex Precedence

Severity: CRITICAL  
Confidence: CONFIRMED  
Status: FIXED — RUNTIME VERIFICATION PENDING (Nginx config updated; live cutover deferred)  
Component: Nginx Reverse Proxy (`deploy/nginx/onusly.conf` / `/etc/nginx/conf.d/onusly.conf`)  
Environment: Production (`https://onusly.duckdns.org`)  
Affected versions or commits: `db9cb11`

**1. What is the issue?**  
Authenticated proof image URLs ending in `.png`, `.jpg`, `.jpeg`, `.gif` (e.g. `/uploads/proofs/<file>.png`) are intercepted by Nginx's nested static asset cache regex inside `location /` instead of being proxied to Go `:8080`, resulting in `HTTP 404 Not Found` from `/var/www/onusly/frontend/dist`.

**2. Expected behavior**  
All `/uploads/...` requests (regardless of extension: `.png`, `.jpg`, `.jpeg`, `.gif`, `.webp`, `.pdf`, `.txt`) must proxy to Go (`127.0.0.1:8080`), enforce JWT auth (`401` unauthenticated), and serve uploaded proof files from `/opt/onusly/uploads/`.

**3. Actual behavior**  
Only `.webp`, `.pdf`, and `.txt` reach the Go backend (`401` unauthenticated). Requests to `/uploads/proofs/*.png`, `*.jpg`, `*.jpeg`, and `*.gif` are handled locally by Nginx's static root `/var/www/onusly/frontend/dist` and fail with Nginx `404 Not Found`.

**4. Why is it happening?**  
Confirmed root cause in `/etc/nginx/conf.d/onusly.conf` (`deploy/nginx/onusly.conf:203-233`):  
- API proxy location uses regular expression `location ~ ^/(goals|...|uploads|approvals|downloads)` (line 203).  
- Frontend SPA block `location /` (line 218) nests `location ~* \.(?:css|js|woff2?|svg|png|jpg|jpeg|gif|ico)$` (line 228).  
- Because `location /` is the matching prefix block and contains a nested regex location covering `png|jpg|jpeg|gif|svg|ico`, Nginx routes `/uploads/proofs/*.png` (and `.jpg/.jpeg/.gif`) to the static `dist` root instead of `proxy_pass http://onusly_backend`.

**5. Evidence**  
Live HTTP probes against `https://onusly.duckdns.org` executed at `2026-11-27T02:07:48+05:30` (`2026-11-26T20:37:48Z`):
```text
GET /uploads/proofs/nonexistent.png  -> http=404 (body: <center><h1>404 Not Found</h1></center><hr><center>nginx/1.30.4</center>)
GET /uploads/proofs/nonexistent.jpg  -> http=404
GET /uploads/proofs/nonexistent.jpeg -> http=404
GET /uploads/proofs/nonexistent.gif  -> http=404
GET /uploads/proofs/nonexistent.webp -> http=401 (Go: missing authorization header)
GET /uploads/proofs/nonexistent.pdf  -> http=401
GET /uploads/proofs/nonexistent.txt  -> http=401
```
Source reference: `deploy/nginx/onusly.conf:203-233`, `/etc/nginx/conf.d/onusly.conf` lines 1239–1267 (`nginx -T`).

**6. Steps to reproduce**  
1. Upload a PNG or JPEG screenshot proof via `POST /uploads` or `SubmitProofModal`.  
2. Open the returned `/uploads/proofs/<id>.png` URL in Approval Center / EvidenceLightbox.

### [API-002] — 13.1 MB Binary Downloads & 50 MB Uploads Proxied Through Go `:8080` with `30s` `WriteTimeout` and Disk Proxy Buffering

Severity: MEDIUM  
Confidence: CONFIRMED  
Status: FIXED — RUNTIME VERIFICATION PENDING (Nginx direct downloads + Go SetWriteDeadline added)  
Component: Go HTTP Server (`cmd/server/main.go`) & Nginx (`deploy/nginx/onusly.conf`)  
Environment: Production (`https://onusly.duckdns.org`)  
Affected versions or commits: `db9cb11`

**1. What is the issue?**  
Large static installer/APK downloads (`/downloads/OnuslySetup.exe` `13.16 MB`, `onusly.apk` `2.68 MB`) and large proof uploads (`/uploads` up to `50 MB`) share Go's `http.Server` (`ReadTimeout: 30 * time.Second`, `WriteTimeout: 30 * time.Second`), and Nginx proxies `/downloads/` through `:8080` causing disk proxy buffering warnings.

**2. Expected behavior**  
Static `/downloads/` artifacts should be served directly by Nginx from disk (`alias` / `root` with proper MIME types and `sendfile on`) with zero Go goroutine or `30s` timeout involvement; proof uploads/streams should allow `http.ResponseController.SetWriteDeadline` / longer timeouts (`>= 120s`) matched to Nginx `proxy_read_timeout`.

**3. Actual behavior**  
Live Nginx error log (`2026-11-26T19:30:51Z`) recorded:
`[warn] *314 an upstream response is buffered to a temporary file /var/lib/nginx/tmp/proxy/1/00/0000000001 while reading upstream, client: ..., request: "GET /downloads/OnuslySetup.exe HTTP/2.0", upstream: "http://127.0.0.1:8080/downloads/OnuslySetup.exe"`
Measured live `onusly.apk` (`2.68 MB`) took `4.07s`; a `13.1 MB` `OnuslySetup.exe` over ~3.5 Mbps mobile tethering exceeds `30s` and will be abruptly severed mid-download by `cmd/server/main.go:860`.

**4. Why is it happening?**  
Nginx passes `/downloads/*` to `http://onusly_backend` (`cmd/server/main.go:298,859-860`), where Go enforces a hard 30-second socket read/write deadline.

**5. Evidence**  
- `cmd/server/main.go:281-298, 856-862`  
- EC2 `/var/log/nginx/error.log` lines 378–379 (`2026-11-26 19:30:51Z`, `19:30:53Z`)  
- Live timing probe: `onusly.apk` `2,678,547` bytes took `4.071s` (`~658 KB/s` from Asia/Kolkata; extrapolated `13.16 MB` ~20s, dangerously close to `30s`).

**6. Steps to reproduce**  
Throttle connection to <= 3 Mbps (e.g. Fast 3G) and download `https://onusly.duckdns.org/downloads/OnuslySetup.exe`, or inspect `/var/log/nginx/error.log` after downloading `.exe` artifacts.

**7. User and system impact**  
Slower-connection users fail mid-download of the Windows installer or timeout uploading 32–50 MB documents, while Nginx burns extra root EBS I/O buffering files from `:8080` to `/var/lib/nginx/tmp/proxy`.

**8. Recommended resolution**  
Serve `/downloads/` directly in Nginx (`location ^~ /downloads/ { alias /opt/onusly/frontend/public/downloads/; ... }` or sync into `/var/www/onusly/downloads/`) with MIME types for `.crx`, `.apk`, `.xml`, and `.exe`, and raise Go `ReadTimeout`/`WriteTimeout` or use per-handler `http.ResponseController` deadlines on `/uploads`.

**9. Verification criteria**  
`HEAD /downloads/OnuslySetup.exe` serves directly from Nginx with zero `upstream response is buffered` warnings in `error.log` and succeeds under bandwidth throttling > 30s.

## I. Security Findings

- **Verified Vulnerabilities / Weaknesses:**
  1. `[SECURITY-001]` (**CRITICAL**): `GET /uploads/` verifies valid JWT only, permitting cross-user access to `/uploads/proofs/<filename>` for non-Nginx-blocked extensions (`.webp`, `.pdf`, `.txt`) without goal ownership or approver verification.
  2. `[SECURITY-002]` (**HIGH**): `RequireUserToken` and `RequireDeviceToken` middleware are unwired in `cmd/server/main.go`, enabling 30-day `device` JWTs to call user-plane endpoints (`POST /goals`, `DELETE /goals`, `POST /auth/revoke-all`, `POST /.../approval`); `Revoke All Sessions` skips `device` tokens and fails open on validator DB errors; `GetBlocklist` misses `X-Device-ID` revocation on user JWTs.
  3. `[SECURITY-003]` (**MEDIUM**): Missing `Strict-Transport-Security` header; 7-day JWT persisted twice in browser `localStorage` despite `HttpOnly` cookie; `auth.js` `isAuthenticated()` catches decode errors and returns `true`; Android `AuthManager` falls back to plaintext `SharedPreferences` on KeyStore failure; legacy unused GCP Client ID `316293252544-...` trusted in `internal/auth/service.go`.
  4. `[WIN-002]` (**HIGH**): `OnuslySetup.exe` launches an unprivileged user-session VBS runner under `HKCU\...\Run`, allowing trivial Task Manager kill or folder deletion without admin elevation.
  5. `[AWS-004]` (**MEDIUM**): User email addresses and handles logged in plaintext to systemd journal on WebSocket connect (`internal/realtime/hub.go:212`).
- **Verified Sound Security Controls:**
  - `/health/warm` (`403`) and `/metrics` (`403`) blocked externally by Nginx; Go refuses non-loopback bind without `ALLOW_INSECURE_BIND=true`.
  - Unauthenticated `/goals`, `/approvals/inbox`, `/users/me`, `/notifications`, `/friends`, `/wellbeing/summary`, `/enforcement/desktop/status` all enforce `401`.
  - CORS `OPTIONS` from `https://evil-attacker.example` properly rejected (`403`).
  - `GET /auth/google/login` sets CSRF `oauth_state` cookie (`HttpOnly; Secure; SameSite=Lax`).
  - Backend `/uploads/` applies strict `sandbox; script-src 'none'` CSP and content MIME sniffing; `Goal.IsApprover` & `approval.Service.Decide` enforce owner/approver isolation and atomic conditional transitions (`TransactWriteItems`).
- **Areas Not Conclusively Runtime-Tested:**
  - Cross-account live API exploits (IDOR tests with two live signed-in QA accounts A & B) were deferred per safety rules (no designated QA OAuth accounts available); verified via source inspection.
  - Windows pipe impersonation & ACL security boundaries verified statically only (`NOT TESTED` on live Windows host).

## L. Recommended Remediation Order

1. **Critical Security & Production Outage Blockers (`SECURITY-001`, `API-001`, `PROOF-001`):**
   - Authorize `GET /uploads/` per goal owner / assigned approver / chat participant and migrate proof storage to encrypted S3.
   - Emit `auth.success` immediately in `ServeWSWithValidator` cookie pre-auth path (`internal/realtime/handler.go:278-284`) so WebSockets stay authenticated.
   - Fix Nginx `/etc/nginx/conf.d/onusly.conf` (`location ^~ /uploads/` + stop nesting global extension cache regex over proxy paths).
2. **Production Availability & Infrastructure Survival (`AWS-001`, `WEB-001`, `AWS-002`):**
   - Expand EC2 root EBS (>= 20–30 GB), enable encryption, prune EC2 Go caches & old `.bak` binaries.
   - Separate SPA routes from API routes cleanly (prefix APIs under `/api/` or route `Accept: text/html` to `index.html`).
   - Provision `proof-events` and `approval-events` SQS queues + DLQs in `eu-north-1` and set their URLs in `/etc/onusly/onusly.env`.
3. **Authentication, Authorization & Revocation (`SECURITY-002`, `SECURITY-003`):**
   - Attach `RequireUserToken` / `RequireDeviceToken` in `cmd/server/main.go`; enforce `token_version` & `X-Device-ID` revocation fail-closed; remove legacy unused OAuth client ID; add `Strict-Transport-Security`; harden frontend `auth.js` `isAuthenticated()` and eliminate dual `localStorage` JWTs / Android plaintext SharedPreferences fallback.
4. **Backend & Database Consistency (`AWS-003`, `GOAL-001`):**
   - Stop masking DB failures as `200 []` (`GET /goals`) or `nil` (`enforcement`, `proof`, `approval` repos); remove `FindByID` full-table `Scan` fallback in production; fix `rejected` vs `active` contract across Dashboard/Goals/docs and disallow orphaned untargeted `"community"` goals.
5. **Windows Installer, Service Security & Native Messaging (`WIN-001`, `WIN-002`, `WIN-003`):**
   - Fix `SECURITY_SQOS_PRESENT | SECURITY_IDENTIFICATION` flags in `desktop/installer/cmd/installer/main.go`; unify `OnuslySetup.exe` on elevated `LocalService` (`Program Files` / `ProgramData` ACLs) + Add/Remove Programs uninstaller + code signing; swap `dial_windows.go` default pipe to `OnuslyAgentIPC`; update `install.ps1` defaults to `onusly.duckdns.org`.
6. **Observability & HTTP Delivery (`AWS-004`, `API-002`):**
   - Add CloudWatch alarms + disk/memory monitoring; remove PII emails from `hub.go` logs; serve `/downloads/` directly via Nginx and extend `/uploads` write deadlines.
7. **Frontend Mobile Layout, Landing Accuracy & Performance (`WEB-002`, `WEB-003`, `PERF-001`):**
   - Fix landing mobile navbar responsiveness (`film.css`) eliminating the `523px` viewport expansion; remove false macOS claim, add Android `.apk` card, add `/privacy` & `/terms` pages, add `/favicon.ico`, and code-split `App.jsx` routes with `React.lazy`.

## M. Final Assessment

1. **Can a new user register and use ONUSLY?**
   Partially: Landing -> Google Sign-In (`GET /auth/google/login` / GSI modal) initiates properly, **but** mobile landing layout breaks (`523px`), refreshing any subpage except `/dashboard` returns raw `401`/`404` (`WEB-001`), and live WebSockets break after 6s (`API-001`).
2. **Can a user reliably create and manage goals?**
   Backend `Create`/`Update`/`Delete` authorization and validation logic is well-tested, **but** UI refreshes on `/goals` fail in Nginx (`WEB-001`), `GET /goals` masks DynamoDB failures as empty lists (`AWS-003`), rejected goals vanish from Dashboard active lockouts (`GOAL-001`), and untargeted `community` goals get stranded (`GOAL-001`).
3. **Does restriction enforcement actually work?**
   Extension unit logic (`140/140` JS tests) and Go/Android policy code are well-structured, **but** on Windows, `OnuslySetup.exe` fails IPC pairing (`WIN-001`) and runs unprivileged in `HKCU` where users can terminate it in Task Manager or skip DNS changes (`WIN-002`), while live Windows runtime was not testable here.
4. **Does proof submission work?**
   Text, `.webp`, `.pdf`, and `.txt` proofs reach Go (`POST /uploads` / `POST /goals/{id}/proofs`), **but ALL `.png`, `.jpg`, `.jpeg`, and `.gif` proof images return `HTTP 404` from Nginx in production (`PROOF-001`)**, and `/uploads/` lacks cross-user authorization (`SECURITY-001`).
5. **Can an authorized partner review and approve?**
   Core backend approval transactions (`CreateDecision`) are atomic and well-guarded, **but** approvers cannot view standard PNG/JPG proof images (`PROOF-001`), live approval notifications over WS fail (`API-001`), and refreshing `/approvals` returns `401` (`WEB-001`).
6. **Are restrictions released correctly?**
   Backend state transitions and blocklist hashing are sound, **but** real-time WebSocket unlock push (`goal.unlocked`) fails in production due to `API-001`, forcing clients to rely solely on polling intervals, and device revocation is unchecked for user-token extension syncs (`SECURITY-002`).
7. **Does the Windows application work reliably?**
   **No (confirmed architectural/IPC defects `WIN-001`, `WIN-002`, `WIN-003`; runtime `NOT TESTED` due to missing Windows VM).**
8. **Does AWS infrastructure appear correctly configured?**
   **No.** IAM role, DynamoDB PITR, Let's Encrypt TLS, and keepwarm work, **but** root EBS (`vol-087b33f32d9b0d6ca`) is `91%` full and unencrypted (`AWS-001`), SQS queues don't exist (`AWS-002`), CloudWatch has zero alarms (`AWS-004`), and Nginx misroutes `/uploads/*.png` and SPA paths (`PROOF-001`, `WEB-001`).
9. **Are there major security risks?**
   **Yes.** Lack of resource-level authorization on `GET /uploads/` (`SECURITY-001`), unused token-type isolation allowing `device` tokens onto user routes (`SECURITY-002`), unprivileged Windows `OnuslySetup.exe` runner (`WIN-002`), unencrypted EBS + local proof storage (`AWS-001`), and missing HSTS / dual `localStorage` JWTs (`SECURITY-003`).
10. **Is the product safe to continue operating in production?**
    **Not without remediation.** Fix `API-001`, `PROOF-001`, `SECURITY-001`, `WEB-001`, `AWS-001`, and `WIN-001`/`WIN-002` before onboarding real users.
